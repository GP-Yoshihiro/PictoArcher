# 少ないトークンで進める

## なぜ
トークンの大半は「読むこと」（ログ、XML、画像、ファイル全体）と「決まった上乗せ」（サブエージェント1体ごとの準備）に使われる。要約を読み、画像は切り取り、質問はまとめる。

## どこにトークンが使われるか
| 原因 | 大きさの目安 | 減らし方 |
|---|---|---|
| メインのセッションが毎ターン自分の会話を読み直す | 1日の半分以上 | 1セッション＝1タスク、終わったら `/clear`、ターンを減らす |
| 「理解するため」にファイルやログを読む | 1,500行のファイルで約2万 | アウトライン・grep・範囲を絞った Read（`minimal-read-edit`） |
| サブエージェントの上乗せ | 1体あたり数万 | 小さい質問はまとめる。役割に合うモデルを使う |
| Unity のログ・テスト結果の XML | 生のままだと十数万 | 失敗の行だけ抜き出す（`log-triage`） |

## やり方
- **ログ：** `cat` しない。`grep -E "error CS|error:|failed" <log> | sort -u | head`、テスト結果は `grep -n 'result="Failed"' Logs/editmode-results.xml | head`。長いものは `log-triage` に渡す。
- **長いコマンド**（ビルド、2分を超えるテスト）：バックグラウンドで動かす。終わると知らせが来るので、待つ間に何度も確かめない。
- **ファイル：** `grep -n` で場所を見つけてから、`offset`／`limit` を付けて Read。直したばかりのファイルは読み直さない。
- **直し：** 1つのファイルの小さい置き換えが多いときは、目印が1回だけ出ることを確かめるスクリプトでまとめる。
- **サブエージェント：** 作業が本当に並べられるときか、新しい文脈が要るときだけ。同時に2〜3体まで。字数の上限と答えの形を伝える。小さい質問は1体にまとめる。
- **画像：** 話題の所だけ切り取り、800px 以下に縮める。
- **確かめ方：** 一番狭いテストから（EditMode → PlayMode → ビルド）。

## 役割ごとのモデル
| 役 | モデル | 向いている仕事 |
|---|---|---|
| `transcriber` | haiku | 計画にコードが全部書いてあるタスクを写して、テストする |
| `log-triage` | haiku | 長いログから失敗と原因だけを抜き出す |
| `task-reviewer` | sonnet | 1タスクごとの確認（仕様に合っているか＋コードの質） |
| メインのセッション | 既定 | 計画、判断、統合、文章で書かれたタスク |

## よくある失敗
- 1つのセッションでいくつものタスクを続ける（文脈がふくらみ、1回のやり取りが何倍も高くなる）。
- 知らせが来るたびに、何もしない返事を1ターン使う。
- 小さい質問ごとにサブエージェントを1体ずつ出す。
- 失敗を探すためにテスト結果の XML を全部読む。
- 1行のロジックの変更を確かめるために、テストで足りるのにビルドし直す。
