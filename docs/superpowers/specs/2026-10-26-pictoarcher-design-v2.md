## 1. 目的と理由

アーチャー伝説（Archero）型のローグライトアクションを、**文字を一切使わずに**作る。【決定】

前提は次の3つ。【決定】

1. 文字ゼロ（数字・記号・ピクトグラムは使ってよい）
2. 初見で分かる（説明なしで遊び始められる）
3. 動かして面白い（触った瞬間に気持ちいい）

**見た目はヴァンサバ（Vampire Survivors）のような2Dドット絵、仕組みはアーチャー伝説**を使う。【決定】
ヴァンサバから取り入れるのは見た目と雰囲気だけ。敵の数は原作のアーチャー伝説のように少なめにし、1体ずつの動きと予兆を見て避ける遊びにする。【決定】

コンセプトは **「撃ちながら避け続ける。強くなるほど弾が目に見えて増える」**。【提案】
強化の結果が必ず画面上の見た目の変化として現れるようにすることで、文字の説明がなくてもスキルの意味が伝わる。

世界観は SF かファンタジーのどちらかで、チームで決める。【決定】この設計書は世界観に関係なく決まる部分をまとめ、世界観ごとの中身と工数は別の2つの文書に書く（§14）。

## 2. ゴール／やらないこと／失敗とみなすこと

**ゴール**
- 1つのステージ（50ウェーブ）を、説明なしで最初から最後まで遊び切れる
- 初見の人が下の「合格ライン」（§15）を満たす

**やらないこと（8週間の範囲外）**
- 2つ目のステージ【決定】
- スマホ対応、オンライン要素、課金や広告、装備、図鑑、デイリー要素
- 敵の大群（画面を埋める数十体〜百体の敵）【決定】
- プレイ途中の保存（1回のプレイは通しで遊ぶ）【提案】
- 🏹強化（ホームでの永続強化）と ⚙ 設定画面。手が空いたら足す候補にする（§13）【提案】

**失敗とみなすこと（動いていても失敗）**
- 画面のどこかに文字が1つでも出る（ロゴ、素材、エラー表示、ウィンドウタイトルの扱いは §5）
- 初見の人が「何をすればいいの？」と口にする
- スキルを選んでも何が変わったか分からない
- 50ウェーブの途中で「同じことの繰り返し」に感じて飽きる【提案】

## 4. 操作とコア体験

| 操作 | 内容 | 出所 |
|---|---|---|
| 移動 | WASD／矢印キー、またはマウス左ボタンを押したままドラッグ（押した位置が仮想スティックの中心） | 【提案】 |
| 射撃 | **常に自動射撃。移動中も撃てる**。一番近い敵を自動で狙う | 【決定】移動中も可／【提案】自動照準 |
| カード選択 | クリック、または 1 2 3 キー | 【提案】 |
| 一時停止 | Esc で ⏸ | 【提案】 |

- 移動中の連射速度は調整用の値として用意する（初期値は止まっているときと同じ 100%）。【提案】
- 敵がいないときは撃たない。【提案】
- 被弾したら短い無敵時間（点滅）。【提案】

## 5. 文字ゼロのルール（全員必読）

前の版から変えない。【決定】

| 項目 | ルール |
|---|---|
| 禁止 | アルファベット・ひらがな・カタカナ・漢字すべて。`LV` `HP` `BOSS` `x2` `s`（秒）などの略語・単位も禁止 |
| 代わりの表記 | レベル `★5`／倍率 `×2`／時間 `⏱ 30`／割合 `+20%`／進行 `23/50` |
| 色の意味 | 赤＝危険・攻撃／緑＝回復／黄＝コイン・経験値／青＝防御・氷／紫＝レア。この5色は UI・拾うもの・エフェクトの意味だけに使い、敵の体の主な色やフィールドの照明には使わない（敵は灰・白・黒・茶・桃などから選ぶ。プレイヤーの弾は白）【提案】 |
| 予兆 | 敵の攻撃は必ず先に赤い線・赤い円で予告する |
| 操作の案内 | 手・矢印キー・マウスの絵のアニメで見せる。キーの絵に英字（W A S D、Esc など）を描かない |
| 絵文字 | フォントで出さない。すべてスプライト画像（ドット絵）で用意する |
| フォント | TextMeshPro のフォントアセットには **数字と記号だけ** を登録する。ドット絵に合うピクセルフォントを使う【提案】 |
| ボタン | ▶ 開始／⏸ 一時停止／↻ やり直し／🏠 ホーム／⚙ 設定／🔒 ロック中／🔊 音量 |
| 素材 | 取り込む前に文字が入っていないか確認する（UIパックの「PLAY」、看板、ロゴ、背景の張り紙や画面の表示など） |
| ウィンドウ・起動画面 | ウィンドウタイトルとアプリ名は OS が表示するもので画面内ではないため対象外。Unity のスプラッシュ画面は、出せない場合の扱いをチームで判断する【提案】 |

## 6. ゲーム進行フロー

```
[起動]
  ├ 初回 → タイトルを出さずにチュートリアル（ウェーブ0）へ
  └ 2回目以降 → ホーム
[ホーム] ▶／これまでの最高記録 `37/50`（クリア済みなら ⏱ 最短タイム）
   ↓ ▶
[プレイ] 1つのフィールドで 50ウェーブ
   ↓
[クリア] 🏆 ＋ ⏱ クリアタイム ＋ 獲得コイン → ↻ ／ 🏠
[死亡]   💀 → 到達ウェーブ `23/50` と取得スキルのアイコン → ↻ ／ 🏠
```

- フィールドは1画面に収まる広さで、カメラは動かない。【決定】
- 今のウェーブの敵を全部倒すと、同じフィールドに次のウェーブの敵が出てくる。【決定】
- 死亡するとそのプレイは終わり、スキルはリセット。【提案】
- 1回のプレイ（50ウェーブ）は 20〜30分を目安にする（1ウェーブ平均 30秒前後）。【提案】
- 保存するもの：最高到達ウェーブ、最短クリアタイム、コイン。保存方法は JSON ファイル。【提案】

### 1ウェーブの流れ【提案】
1. 敵が出る位置に赤い `!` 円 → 敵が出現
2. 戦闘
3. 全滅 → 経験値とコインが自分に吸い寄せられる
4. 約1.5秒の休み（画面上部の `23/50` が `24/50` に変わる） → 1 に戻る

### 50ウェーブの構成【提案】

| ウェーブ | 内容 |
|---|---|
| 5・15・25・35・45 | 中ボス（出る前に ⚠ が点滅） |
| 10・20・30・40 | ボス（画面上部に 💀 付きのHPバー） |
| 50 | 最後のボス |
| 11・21・31・41（ボスの直後） | 天使（♥回復 か スキル1つ を選ぶ）。敵は出ない |
| それ以外 | 通常のウェーブ |

- 敵の種類は少しずつ増やす。1〜9：2種／11〜19：+1種／21〜：+1種（全4種）。31〜は組み合わせと強化版で変化を付ける。
- 中ボスとボスは同じものが繰り返し出るので、出るたびに HP と速さを上げ、ボスは攻撃パターンも足す（§8）。
- 強化版の敵は、見た目を少し大きくし、色を濃くする（§5 の5色にはしない）。
- 10ウェーブごとに、フィールドの色合い（時間帯や照明）を少し変えて、進んでいる感じを出す。背景の素材はそのまま使う。色合いは彩度を抑え、§5 の5色に見えないようにする。

### レベルアップ【提案】
経験値バーが満タン → 時間停止 → カード3枚 → 1枚選ぶと再開。ウェーブの途中でも発生する。
50ウェーブで 20回前後のレベルアップを目安にする（調整値）。全スキルが上限に達したら、カードは ♥回復 と コイン に置き換える。

### 一時停止メニュー【提案】
▶ 再開／↻ やり直し／🏠 ホーム／🔊 音量

## 7. チュートリアル（ウェーブ0）【提案】

1. 敵1体だけ。矢印キーとマウスの絵がアニメで動きを見せる → プレイヤーが動く
2. 近づくと自動で弾が飛ぶ → 撃つのは自動だと分かる
3. 1体目を倒すと必ずレベルアップ → カード選択を一度体験させる
4. 2体目は弾を撃つ敵。赤い予兆線を見せて、避けることを覚えさせる
5. 倒すと `1/50` が出て、そのままウェーブ1が始まる

案内の絵はプレイヤーが一度その操作をしたら消える。2回目以降の起動では出さない。

## 8. 敵とボス

敵は「役割」で決め、見た目と名前は世界観ごとに決める（§14）。【提案】

絵を描く量に合わせて、通常の敵は4種、中ボスは1種、ボスは2種にする。【提案】（週3日では絵の担当の工数が足りないため。§13）

### 通常の敵（4つの役割）【提案】
| 役割 | 動き | 予兆 | 登場 |
|---|---|---|---|
| 追う敵 | プレイヤーを追ってくる、体当たり | なし（遅い） | 1〜 |
| 撃つ敵 | 止まって狙い、まっすぐ撃つ | 赤い線 | 1〜 |
| 固定砲台 | 動かず、円形に弾をばらまく | 光ってから撃つ | 11〜 |
| 自爆する敵 | 突進して自爆 | 赤い円が広がる | 21〜 |

前の案にあった「速い敵（速く不規則に飛ぶ）」は作らない。絵の担当に余裕が出たら足す候補にする（§13）。

### 中ボス（1種）【提案】
- HPが減ると分裂する。5・15・25・35・45 に出る。
- 出るたびに HP と速さを上げ、分裂の数を増やす。

### ボス（2種）【提案】
| ボス | 出るウェーブ | 攻撃 |
|---|---|---|
| ボスA | 10・20・30・40 | 10：突進（赤い線）／雑魚を呼ぶ（赤い `!` 円）。20 から範囲攻撃（赤い円）を足す。30・40 は HP と速さを上げ、攻撃の間隔を短くする |
| 最後のボス | 50 | 3パターン：突進／弾幕（光ってから）／雑魚を呼ぶ。HPが半分を切ると色と光り方が変わり、間隔が短くなる |

- ボスAの範囲攻撃は、新しいコマを描かず「ため」の動きを使い回す。
- 最後のボスの見た目の変化は、プログラマーが色と光り方で出す（変化のコマは描かない）。
- 強化版の色は §11 のとおりプログラマーが出す。

数値（HP・攻撃力・速度・出現数）はすべて ScriptableObject の調整値として扱い、プレイテストで決める。

## 9. スキル（12種）【提案】

前の版から変えない。弾や玉の見た目だけ世界観に合わせる（§14）。
カードには **大きいアイコン＋数字＋約1秒の実演アニメ** を入れる。

| アイコン | 効果 | 画面での見え方 | 重ね取り |
|---|---|---|---|
| ⇉ | 前方の弾 +1 | 弾が並んで飛ぶ | 最大3 |
| ↖↗ | 斜めの弾 | V字に飛ぶ | 最大2 |
| ⇄ | 後ろにも撃つ | 背中側にも弾 | 1回 |
| ⤳ | 貫通 | 敵をすり抜ける | 1回 |
| ⟲ | 壁で跳ね返る | 壁で反射 | 最大2 |
| 🔥 | 炎 | 燃えて継続ダメージの数字 | 最大3 |
| ❄ | 氷 | 青くなり遅くなる | 最大3 |
| ⚡ | 連射 +% | 撃つ間隔が短くなる | 最大5 |
| 💥 | クリティカル | 大きい黄色の数字 | 最大5 |
| ⚔↑ | 攻撃力 +% | 弾が大きく光る | 最大5 |
| ♥↑ | 最大HPアップ＋回復 | HPバーが伸びる | 最大5 |
| ◎ | 周りを回る玉 | 自分の周囲を玉が回る | 最大3 |

- 重ね取りの段階はカードに `★★` のように表示する。
- 上限に達したスキルはカード候補から外す。
- カード3枚は重複なしでランダム。重み付けは調整値。
- 実演アニメは、ゲームの実際のスプライトを使ってプログラマーが作る（UI担当はカードの枠と並べ方を作る）。

## 11. ドット絵の方針【提案】

細かい見た目（線の有無、色の数、陰影の付け方、キャラの頭身）はデザイナーが決める。ただし、工数は下の大きさを前提に見積もっているので、大きさを変えるときは工数も見直す。

| 項目 | 前提 |
|---|---|
| 描画の基準解像度 | 480×270（1920×1080 の 4倍拡大）。URP 2D の Pixel Perfect Camera を使う |
| フィールド | 1画面＝480×270 の中に収める（壁を含む）。HUD はフィールドの上に重ねる。戦える広さは壁の内側でおよそ 440×220 |
| タイル | 16px のマス目を基準にする（フリー素材もこの大きさのものを選ぶ） |
| プレイヤー・通常の敵 | 24〜32px 四方 |
| 中ボス | 48〜64px 四方 |
| ボス | 64〜96px 四方 |
| スキルアイコン | 32px 四方（カードでは 2倍で表示） |
| HUD のピクトグラム | 16px 四方 |
| 向き | 左右だけ（右向きを描き、左は反転）。上下の向きは描かない |
| 被弾の白い光り | プログラマーがシェーダーで出す（コマを描かない） |
| 強化版の色 | プログラマーが色を変えて出す（別の絵を描かない） |

- 背景とエフェクトはフリー素材なので、キャラの絵柄と合うかを最初の1週目に確かめる。合わない場合は、素材側の色をプログラマーが合わせる。大きさが合わず使えない場合は、別の素材を探す（描き直しはしない）。
- フリー素材は CC0 を優先する。CC-BY は、クレジットをゲームの外（README と配布ページ）に書けば使ってよい。素材を買う予算は無いものとする。
- 絵の受け渡し：絵の担当は PNG のスプライトシート（コマを横一列、1コマの大きさをそろえる）で渡す。Unity への取り込みとアニメの設定は、そのキャラや敵を担当するプログラマーが行う。
- 絵が届くまでは、プログラマーは仮の図形で作り、届いたら差し替える。
- 全員の素材について、間に合わない場合の代わり（仮の図形、既存の絵の流用）を先に決めておく。

## 12. 技術方針【提案】

| 項目 | 方針 |
|---|---|
| テンプレート | Unity 6 の 2D（URP 2D Renderer）テンプレートで作成済み |
| ドット絵 | Pixel Perfect Camera（基準 480×270）。画像は Filter Mode を Point、圧縮なしで取り込む |
| 入力 | Input System。キーボードとマウスのドラッグを同じ「移動ベクトル」に変換する |
| データ | スキル・敵・ウェーブの構成は ScriptableObject。新しいスキルや敵、ウェーブはデータを足すだけで増やせるようにする |
| 文字 | TextMeshPro、数字と記号だけのピクセルフォントのアセット |
| シーン | Boot／Home／Run の3つ。Run シーンはフィールド1つで、ウェーブはデータを順に読んで敵を出す |
| 共同作業 | シーンを同時に編集しない。担当ごとにプレハブを分け、シーン編集は1人に決める。UnityYAMLMerge を各自設定する |
| Claude のルール | リポジトリの一番上に `CLAUDE.md` を置き、全員の Claude が同じルールで動くようにする。書くのは次の4つ：文字ゼロのルール（§5）、フォルダ構成、テストの書き方、「シーンは担当の1人だけが編集する」。1週目に Cさんが作り、3人で確認する |
| ブランチ | 担当ごとにブランチを分ける。`main` へは直接入れず、ほかの1人が確認してからマージする。Claude が書いたコードも、マージ前に人が読む |
| ビルド | Windows と Mac のスタンドアロン |
| テスト | 純粋なロジック（ダメージ計算、スキルの重ね取り、カードの抽選、ウェーブの進行）は EditMode テストを書く |

## 13. 分担・工数・スケジュール・削る順【提案】

### 分担

- **Bさん（プログラマー）：敵**（敵AI 4種、中ボス1種、ボス2種、予兆表示、被弾の光りと強化版の色、敵のアニメの組み込み）
- **Cさん（プログラマー）：進行とUI**（ウェーブの進行と50ウェーブの構成、ホーム、カード選択、HUD、結果画面、チュートリアル、音、保存、フリー素材の取り込みと素材一覧、文字ゼロのルール管理、`CLAUDE.md`）
- **スキル系UI担当**：スキルアイコン12種、カードの枠、HUD とボタンのピクトグラム、操作案内の絵、画面のレイアウト
- **キャラ担当**：プレイヤー、通常の敵4種、中ボス1種、ボス2種、天使
- **デザイナー（補助）**：背景の飾り小物（フリー素材の不足分を補う）、宣伝用のキービジュアル（ゲームの外で使う。文字なし）、クリア画面の一枚絵

UI担当とキャラ担当の工数は世界観で変わるので、世界観の文書に書く。

### プログラマーの工数（1人 24人日）

プログラマーは全員 Claude を使うので、次のように見積もる。【提案】
- コードを書く作業（スキルの効果、敵の動き、画面の仕組み、テスト）は、Claude なしの約半分の時間でできると見る。
- Unity エディタでの作業（シーン、プレハブ、アニメの設定）と、遊んで数値を合わせる作業は、Claude を使ってもあまり速くならないと見る。
- 合わせて、Claude なしより3〜4割少ない見積もりになる。**どれだけ速くなるかは推測**なので、2週目の終わりに実際にかかった日数と比べて見直す。

| 担当 | 主な作業 | 見積もり | 余裕 |
|---|---|---|---|
| A | 移動と射撃 2／弾の管理・当たり判定・障害物 1／スキルの仕組み（カード、重ね取り、抽選）2／スキル12種の効果 6／実演アニメ 2／手触り（ヒットストップ、揺れ、ダメージ数字）2.5／経験値とコインの落下と吸い寄せ 0.5／照明と色調の変化 0.5／プレイヤーのアニメの組み込み 0.5 | 17人日 | 7日 |
| B | 敵の土台と予兆と出現 2／通常の敵4種 3／中ボス 1.5／ボス2種（ボスAの強化版を含む）6／被弾の白い光りと強化版の色 1／敵のアニメの組み込み 1.5（SF はプログラムで出す動きが増えて +0.5）／ボスの動きの調整 1 | 16人日（SF 16.5） | 8日（SF 7.5） |
| C | 土台・文字ゼロの仕組み・`CLAUDE.md` 1.5／ウェーブの進行 1／50ウェーブの構成 2／HUD 1.5／カード選択の画面 1／天使 0.5／ホーム・結果・死亡の画面 1／保存 0.5／一時停止 0.5／チュートリアル 2／音 1／フリー素材の取り込み 1.5（SF 2.5）／ビルド 1 | 15人日（SF 16） | 9日（SF 8） |

- 余裕の日は、数値の調整、毎週のテスト、バグ修正（8週目を含む）、Claude が書いたコードの確認にあてる。
- Claude で速くならなかった場合、見積もりは A 約25.5、B 約22、C 約20.5 になる。このときは A だけが約1.5日はみ出すので、下の「遅れたときに削る順」を当てはめる。
- それでも余裕が残ったら、「手が空いたら足す候補」から足す。

### スケジュール
| 週 | プログラム | 絵 |
|---|---|---|
| 1 | 移動・自動射撃・敵1体が動く。データ形式、`CLAUDE.md`、ブランチの運用を決める | 世界観の決定、ドット絵の大きさと色の決定、試作（プレイヤーと追う敵のラフ）。フリー素材の候補を集める |
| 2 | 1つのフィールドで数ウェーブ続けて遊べる（出現 → 戦闘 → 全滅 → 次のウェーブ）。**実際の速さと見積もりを比べる** | プレイヤーの完成。仮アイコン12種と操作案内の最小版（UI担当） |
| 3 | レベルアップとカード3枚、スキル6種、敵3種（追う・撃つ・固定砲台）。**ここから毎週、初見の人でテスト** | 追う敵・撃つ敵、カードの枠 |
| 4 | 全体の流れが入る：50ウェーブ（仮の構成）、中ボス、天使、ボスA、結果画面、保存 | 中ボス、天使、スキルアイコン6種、画面のレイアウト |
| 5 | 中身を揃える：スキル12種、敵4種、ボスAの強化版（20〜40）、チュートリアル | ボスA、HUD |
| 6 | 最後のボス（絵が届くまでは仮の図形）、難易度調整 | 固定砲台・自爆する敵、スキルアイコン残り6種（**アイコンの期限**） |
| 7 | 手触りの仕上げ：ヒットストップ、揺れ、効果音、アイコンの統一。届いた絵を差し替える | 最後のボス、ボタンのピクトグラム、操作案内の完成版（**新しい絵の期限**） |
| 8 | 新機能禁止。バグ修正と最終テスト。最後のボスの絵を入れて調整 | 新しい絵は入れない。直しと統一だけ |

- 絵が届くまでは、プログラマーは仮の図形で作る（§11）。絵の順番は、プログラムで使い始める順に合わせて、デザイナーが入れ替えてよい。
- 最後のボスの絵は7週目に届くので、プログラム側は6週目に仮の図形で動きを仕上げておき、届いたら差し替えるだけにする。

### 遅れたときに削る順
最後のボスの「雑魚を呼ぶ」→ ボスAの範囲攻撃（20〜40 は HP と速さだけ上げる）→ ◎ → 自爆する敵（21〜 は組み合わせだけで変化を付ける）

予兆表示、チュートリアル、カードの実演アニメは「初見で分かる」の柱なので最後まで削らない。

絵が間に合わないときは、仮の図形か、ほかの絵の色違いで出す。どの絵をそうするかは、デザイナーとそのプログラマーで決める。

### 手が空いたら足す候補
プログラマーの余裕が残ったときに、上から足す。絵が要るものは、絵の担当に余裕があるときだけ。
1. ⚙ 設定画面（音量、画面の揺れの強さ）。UI担当の ⚙ アイコンが要る
2. 手触りの仕上げ（エフェクトや音の追加）
3. 速い敵（キャラ担当で約1人日）
4. 🏹強化（ホームでの永続強化。UI担当のアイコンが要る）

### テストのための準備
- 保存データを消して初回状態に戻すデバッグ用の操作（キーの組み合わせ）を用意する
- 好きなウェーブから始めるデバッグ用の操作を用意する（50ウェーブを毎回通しで遊ばないで済むように）
- 操作案内の絵（§7）は、3週目のテストに間に合うよう最小版を先に入れる

## 15. 合格ライン（毎週のプレイテスト）【提案】

説明を一切せずに初見の人に渡して、

1. 30秒以内に自分から動いて敵を倒せるか
2. ウェーブ10のボスまで誰の助けもなく進めるか（ボスAが入る4週目から測る。3週目は「ウェーブ5まで」で測る）
3. スキルカードを選んだあと、その効果を自分で言えるか

テスト中は観察する人も口を出さない。止まった場所と、その人が口にした言葉を記録する。
毎週まだ遊んだことのない人を探す。見つからない週は2回目の人で測り、記録に「2回目」と書く。観察と記録は、その週に手の空いている人が行う。

## 16. 作る人に任せること

- 数値のバランス（HP、攻撃力、経験値の必要量、ウェーブごとの敵の数と組み合わせ）
- フィールドのレイアウト（障害物の配置）
- ドット絵の細かい見た目（§11 の大きさの範囲内で）
- エフェクトや効果音の細かい選び方
- コードの構成（§12 の方針の範囲内で）
